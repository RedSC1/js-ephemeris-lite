# js-ephemeris-lite

用于浏览器和 Node.js 的天文与中国历法库。提供天体位置、节气与月相、
农历转换、干支和太阳时计算，采用纯 JavaScript 实现，附带 TypeScript 类型声明，
无运行时依赖。

行星模型以 VSOP2013 和 TOP2013 为理论来源，月球模型以 ELP/MPP02 为理论来源，
并按 DE441 校准。日月食算法、古代历法资料和部分中国年号记录来自
[《寿星天文历》](https://github.com/sxwnl/sxwnl)。同仓库的 `huangli-lite` 中，
节日资料亦来自该项目，神煞和每日宜忌主要参考
[cnlunar](https://github.com/OPN48/cnlunar)，并由本项目整理修改。完整来源、处理方式与许可见
[第三方声明](./THIRD_PARTY_NOTICES.zh-CN.md)。

个人主页：[redsc1.com](https://www.redsc1.com/)

在线工具箱：[redsc1.com/tools](https://www.redsc1.com/tools)——提供日历、气朔等浏览器工具。

## 安装

需要 Node.js 18 或更高版本；浏览器项目可通过支持 ES modules 的构建工具使用。

```sh
npm install js-ephemeris-lite
```

本文档对应当前 1.0.0 beta 源码；使用已安装版本时，请以该版本随包文档为准。
正式版发布前接口仍可能调整。

## 快速开始

将公历日期转换为农历，或生成一年的节气和月相表：

```js
import { solarToLunar, lunarToSolar, getQiShuoYear } from 'js-ephemeris-lite';

const options = { mode: 'china-astronomical', utcOffsetMinutes: 480 };

const lunar = solarToLunar({ year: 2025, month: 1, day: 29 }, options);
console.log(lunar.month, lunar.day); // 1 1

const solar = lunarToSolar({
  year: 2033, month: 11, day: 1, isLeap: true,
}, options);
console.log(solar);

const year = getQiShuoYear(2026, {
  ...options,
  lunarPhaseAnglesDeg: [0, 90, 180, 270],
});
console.log(year.events); // 节气、朔、上弦、望、下弦
```

需要单独求某次事件时，可用 `solveSolarLongitude(targetRadians, nearJdTT)`
或 `solveNewMoon(nearJdTT)`。完整示例见[历法与时间指南](./docs/time-and-calendar.md)。

## 功能

- 太阳、月球、八大行星及冥王星的位置与速度，提供日心、地心及地月质心接口。
- 完整 TSC1 v1 恒星表读取、别名查询、三维空间运动传播和恒星视位置；默认亮星数据由可选的 `taiyin-star-catalog-lite` 提供。
- 二十四节气、七十二候、朔与指定月相求解。
- 阴阳历互转、闰月，以及中国历史历法和历史纪年查询。
- 年月日时干支、三种晚子时规则、地方平太阳时与真太阳时。
- 太阳高度、日出日落及极昼极夜判断。
- 兼容接口 `ecFast`、`ysPL`、`rsGS`、`rsPL` 的日月食搜索、接触时刻、
  全球食带与地方见食计算。
- 面向应用的[日月食查询接口](./docs/eclipse-search.md)，接受常规日期和角度制
  观测位置，返回全球事件、接触时刻及地方可见性；不包含地图或行政区数据。

[视位置与天象搜索](./docs/sky-events.md)还提供三种参考面、
行星留与黄经穿越、月球照明、天体出没、近远点、交点、大距和赤经事件。
暂不支持小行星；日月食接口的兼容参数和时间约定见
[日月食文档](./docs/eclipses.md)。

> **冥王星精度警告：推荐范围为 1600～2200 年。范围外仍可计算，但使用低精度后备模型，
> 位置、速度及天象时刻均不可视作高精度结果。**
> 计算对象是冥王星系统质心，不是本体中心或光心。
> 详见[精度说明](./docs/accuracy.md#冥王星)及 `PLUTO_MODEL_INFO`。

## 时间、单位与精度

- 位置和定气定朔求解使用 **JD(TT)**；历法、民用时间和地平观测使用 **JD(UT1)**。
  事件的 `time` 是不带时区的 `JulianTime`，用 `.toZonedTime(480)` 显示东八区时间。
  `solve…` 直接返回 `JulianTime`；数学层 `…TimeFast/Accurate` 仍返回 TT JD 数值。
- 几何位置采用 J2000 黄道坐标；行星距离为 AU，地心月球距离为 km。
  其他接口的单位见对应指南。
- 民用日期在 1582-10-15 起采用格里历，之前采用儒略历；天文年号 `0` 表示公元前 1 年。
- 主要星历模型面向天文年 `-6000..10000`，具体查询范围依 API 而异。
  精度随天体、年代和计算模式变化，求根容差不等于天文绝对精度。
- 时间层使用 `UTC ≈ UT1`，不包含闰秒或 EOP 数据；固定时区不自动处理夏令时。

定气定朔三档在 1900～2100 年每 5 年抽样（另含 2026 年，共 1008 个节气和 546 个朔），
相对 C++ DE441 参考链的实测结果如下。
参考链采用 Vondrák 2011 岁差、IAU 2000A 章动、光行时、周年光行差和多星体引力偏折；
速度数据来自同一台 Apple arm64 机器上的 Node.js 25.9.0 热路径，仅用于比较三个 JS 档位：

| Fast | Mid（默认） | Accurate |
| --- | --- | --- |
| **定气误差**：RMS 0.541 秒<br>最大 1.812 秒 | **定气误差**：RMS 0.205 秒<br>最大 0.627 秒 | **定气误差**：RMS 0.135 秒<br>最大 0.490 秒 |
| **定朔误差**：RMS 0.268 秒<br>最大 0.785 秒 | **定朔误差**：RMS 0.191 秒<br>最大 0.814 秒 | **定朔误差**：RMS 0.185 秒<br>最大 0.729 秒 |
| **定气速度**：8.14 µs | **定气速度**：24.69 µs | **定气速度**：129.01 µs |
| **定朔速度**：21.20 µs | **定朔速度**：53.61 µs | **定朔速度**：1105.44 µs |
| 大量排盘、快速预览 | 日历与 App 常规计算 | 高精度校验、研究用途 |

这里的“误差”是相对该参考链的时刻差，不是相对真实天象的统一误差上限；机器、运行时和
日期范围变化后速度与误差分布也会变化。Fast 采用固定阶段求根并在最终修正中使用完整
主黄经级数；结果支持目前的档位定位：Fast 优先速度，Mid
在成本与精度之间取平衡，Accurate 使用完整库内视位置模型。

适用范围、档位选择及限制见[精度说明](./docs/accuracy.md)。

## 作者聊算法与软件（FAQ）

Q：为什么选择 MPL-2.0 许可证？

A：本程序以 MPL-2.0 协议开放源代码，源代码不进行任何混淆或加密处理（之所以特意说明，是因为好像真的有人这么干过🤣。可能当时是为了保护版权，但以现在的眼光看，确实有点让人无语🤣）。选择 MPL-2.0 并不是为了限制商业使用，而是希望如果有人发现并修复了核心代码中的问题，并将修改后的版本用于对外发布，相关修改仍能保持开放，让其他人知道修复了什么，也方便大家共同完善代码。
简单来说：MPL-2.0 允许商用；如果你修改了本项目中受 MPL-2.0 覆盖的文件并向外分发，需要提供这些修改文件的源代码，但不要求整个应用开源。也就是说，如果你把我的 bug 修了，别让这个修复永远埋在某个闭源安装包里。😭 所以，大家按许可证正常使用即可，也没有必要为了源码发布形式本身额外增加复杂的封装、转换或混淆步骤。另外，本包使用的科学模型和历史资料仍应遵守[第三方声明](./THIRD_PARTY_NOTICES.zh-CN.md)中列出的各自条件。

Q：已经有不少轻量天文库和民俗日历库了，为什么还要写这个库？

A：本来一开始只打算把 C++ 版本的 [taiyin-ephemeris](https://github.com/RedSC1/taiyin-ephemeris) 移植到 JavaScript，像 [py-ephemeris](https://github.com/RedSC1/py-ephemeris) 一样提供另一种语言的封装。后来考虑到浏览器环境更需要控制体积和运行成本，才逐渐做成了 js-ephemeris-lite。行星部分采用 VSOP2013（水、金、地、火）和 TOP2013（木、土、天、海），并按 DE441 校准；日月食、历史历法等功能则在同一个时间和星历核心上整合。生成阶段会把基础理论与拟合残差折叠进最终系数表，项目也在 -6000～10000 年范围内做了 DE441 对照。具体来源见第三方声明，精度随天体和年代的变化见 docs 文件夹。

Q：js-ephemeris-lite 的古代历法是怎么做的？

A：包内没有在查询时重新执行整套古历近似算法，而是把整理后的朔、气归日结果编码成分段线性基线，再用稀疏位图压缩 ±1 日修正：一张位图记录修正位置，另一张记录修正符号。这样运行稍快、数据也更紧凑，但代价是分段主要服务于压缩和拟合，不再直接表达原始历法模型的历史含义。古历资料与原始算法的具体来源见[第三方声明](./THIRD_PARTY_NOTICES.zh-CN.md)。

Q：为什么只有每日宜忌，没有时辰宜忌？

A：当前只实现了能够说明资料和规则依据的每日宜忌。很多现代万年历的时辰宜忌包含古书中不可能出现的现代名词，我暂时也没找到足够清楚的理论基础。《钦定协纪辨方书》我自己买了，其中没有一套可以直接照搬的时辰宜忌规则，所以本着负责的态度，没有硬写或者加入自己的观点。以后可以再研究市面软件到底采用了什么表或规则，确认清楚以后再决定加不加。

Q：节日名称和月历显示是怎么处理的？

A：本项目重新整理了节日的正式名称、月历短名称、别名和显示优先级，并补充、校正了部分纪念日。详情页可以保留完整名称和更多记录；月历格只选择优先级最高、适合紧凑显示的短名称，避免多个节日挤在同一格里。

Q：天体位置是怎么算的？

A：水、金、地、火的行星理论来源是 VSOP2013，木、土、天、海来自 TOP2013；生成阶段将它们离线转换、换基并筛选成日心黄道经度、黄纬和距离的直接级数，再按 DE441 做校准。水星至海王星最终统一成儒略千年 `T` 的普通时间幂乘周期项，与经典 VSOP 布局一致。气朔的 fast／mid 路径裁剪 Earth 时，会把同一频率跨越多个时间幂的系数作为一个完整包络保留，避免把长期抵消拆散。生成阶段会形成嵌套的包络优先级，重排各个 Lₙ/Bₙ/Rₙ 系数块，并写出每个档位在各阶中应保留的前缀数量；运行时只需裁掉各阶尾部，不再排名，也不用额外保留一套旧基底。修正系数也折进最终系数表，所以运行时看起来没有单独的修正项。ELP/MPP02 月球级数则经过截断和重排，并把基本角组合整理成共享相位表，让三个坐标可以复用相位计算和解析求导；修正项同样写进了级数。冥王星比较麻烦，上面这些招都不好用，1600～2200 年用了直接拟合 DE441 的 L/B/R Chebyshev 近似，推荐范围外另外放了一套宽年代低精度后备模型。也就最近几百年精度不错，远了只能说：“冥王星大概就在那一块🤓☝️”🤣 先这样吧，弄个很大的包也不一定变好，就不改了。

Q：ΔT（TT−UT1）是怎么算的？

A：古代 ΔT 使用 Stephenson, Morrison & Hohenkerk (2016) 给出的分段三次多项式计算，现代则保存逐年观测估计值和短期预测值，再用 Catmull–Rom 样条插值；-820 年以前使用经典的二次多项式预测，-820～-720 年平滑衔接到论文模型。当前控制点含 IERS 对 2027 年的预测，2027～2028 年使用三次 Hermite 过渡，2028 年以后使用 Stephenson, Morrison & Hohenkerk (2016) 的长期模型，并且我加了一个“神必小修正🤓☝️”。不开玩笑地说，它是一个与月球约 18.6 年周期相关的经验项，在现有独立样本上表现不错。未来 ΔT 本来就无法像星历位置那样精确预测，因为真正难预测的是地球自转。以后有新的观测数据，这部分当然还会继续更新。
顺便说个题外话，我发现有那种算命软件，ΔT 数据十年不更新，里面有一份寿星万年历约 2015 年前后版本的 JavaScript 部分代码，而且还放得挺深，这么久了 ΔT 差了十几秒了已经😅。。。当时翻了好久，各种操作，最后看到了“SSQ🤓☝️、gxc_sunLon🤓☝️”之类的东西我真蚌埠住了。更奇怪的是，其中部分历法功能还额外依赖一份有限年份范围的数据；超出这个范围后，八字起运、流月等功能会失效。原项目本身其实具有节气计算能力，因此这种设计究竟是出于性能、兼容、历史遗留还是其他原因，我无法确认，而且我并不觉得能在 2008 年的 IE 浏览器上跑、性能还很不错的代码，会在 2015 年前后的设备上无法流畅运行。我特意提这件事，是因为我个人不太喜欢一种做法：使用开放源码项目的核心代码，却通过层层压缩、编码等方式把来源“隐藏”起来，同时在产品宣传中只强调“高精度算法”，完全不提原作者。至于具体项目为什么这样实现，我没有足够信息，也就不过度解读了。

Q：为什么不写 astrology-lite？

A：因为我还不知道怎么用比较低的体积和运行成本存储小行星星历数据，所以就没做。以后研究一下。

Q：八字部分要说的吗？

A：八字那边用的都是比较标准的算法，没啥好说的。神煞的说法比较多，最初版本是 AI 整理的，当时自己没逐条检查；现在总体 review 过一遍，也补了测试，不过流派实在太多，不能保证跟所有说法都一致。如果发现明确的规则错误，也欢迎直接提 issue，不能啥都甩锅给流派差异🤣。

Q：JavaScript 版紫微相较于之前 Dart 版的 ziwei_core，为什么差别这么大？

A：最开始设计 Dart 的 ziwei_core 时，发现流派众多，而且紫微斗数的安星法总体可以抽象为几种类型，所以写了一个小型的“解释器”。但是写了前端 UI 之后，发现通过解析 JSON 再解释每条安星规则会产生不必要的运行时开销，而且当时总体还是面向对象的写法；后面觉得这种东西面向过程更合适，所以重构了底层逻辑，把声明式安星规则预编译、压扁成静态查表。当然现在也还支持当年的格式，只不过更推荐用新的 TOML 文件来自定义流派。

Q：你觉得相较 ziwei_core，这个 ziwei-lite 升级的点在哪？

A：一个就是我上面说的重构了底层；二是理论上运行效率变快了，但是因为实现语言不同，我无法真实比较实际上变快了多少。另一个是 ziwei-lite 新增了查看历史年号的功能哈哈哈，虽然没啥用，但是感觉很好玩，后来又根据第三方数据增补了一些。第三个是特殊历法时期现在开启历史历法（默认）以后，会根据历史历法的月份序列推演流月（当然不是瞎排），不会跟之前一样直接熔断。所以在支持的天文年 -6000～10000 范围内仍可排流月；更远即使某些底层计算还能返回结果，也不建议使用，节气时刻和农历归日都没有精度保证。

Q：八字和紫微的排盘准确性怎么样？

A：这里最好把天文历算精度和流派规则是否一致分开看。八字的年、月柱边界取决于节气，日、时柱还会受到时区、太阳时和子时换日规则的影响；紫微斗数的出生日期基础则依赖农历排月，其中同时涉及定气和定朔。本项目的定气定朔精度与测试结果见 [`docs`](./docs/) 文件夹。

八字神煞流派众多，这里主要收录古书可见或流传较广的规则。紫微斗数部分内置了一份常见版本的 TOML 规则文件，其中包含星曜亮度表、四化表及部分存在争议的四化版本。不同流派的结果不完全一致，并不等同于天文计算误差；如果您采用其他规则，也欢迎提出 issue 或补充资料。

Q：紫微斗数的历史历法怎么处理？与其他软件兼容吗？

A：历史模式使用包内整理好的朔气归日资料和月份序列，当前天文事件求根则由本项目自己的实现完成。经小规模抽查，部分古代时期的朔日结果与文墨天机一致；特殊历法月名和改历边界由本项目单独处理并校验。资料来源见[第三方声明](./THIRD_PARTY_NOTICES.zh-CN.md)。不同软件采用的历法数据和排盘规则可能不同，因此这里不承诺与所有软件完全兼容。

Q：为什么写紫微斗数库？你之前的开发者笔记看起来好像并不相信这些？

A：是的。

我以前确实找过同八字的人进行比较，至少从我自己能观察到的样本来看，我们的生活轨迹并没有表现出什么明显的相关性。因此，我目前并没有因为自己写了八字、紫微斗数相关程序，就认为这些传统术数的预测能力已经得到了验证。

但这也不意味着我对传统术数只有简单的“相信”或“反对”两种态度。

我第一次认真研究紫微斗数排盘算法时，真正让我感兴趣的其实不是“它到底准不准”，而是这套规则系统本身。

它仅仅使用出生年月日时，通过一系列非常漂亮的对称关系、顺逆规则、宫位映射和状态转换，就能够生成一个看起来信息量非常庞大的盘面。从信息论角度看，规则本身当然不会凭空增加出生时间所携带的信息；而且在部分规则中，“日”这个变量的利用程度也有限，因此会产生比较高的重盘率。

但也正因为如此，我反而觉得它很有意思：

用很少的输入，通过一套复杂而高度结构化的规则，构造出一个看起来极其丰富的状态空间。

从程序设计的视角来看，我更愿意把它看作一个规模很大、历史悠久，而且设计得颇为精巧的规则系统——甚至可以说是一个很有意思的“状态机”。

这也是我愿意把它实现成程序、研究它的历史历法、排盘边界以及各种特殊规则的主要原因。它是否具有现实预测能力，与它作为一个算法和规则系统是否值得研究，在我看来其实是两个不同的问题。
